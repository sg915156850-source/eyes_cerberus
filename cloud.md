# Eyes Cerberus — Аудит проекта

Дата аудита: 2026-09-04

Eyes Cerberus — это Bash-демон для защиты одного конкретного Linux-сервера: раз в 30 секунд сканирует процессы, сеть и точки персистентности, сверяет их с сигнатурами конкретного инцидента (дроппер `/let` + C2-бэкон на порт 9009, март–апрель 2026), и либо автоматически нейтрализует угрозу (kill + carantine + iptables), либо просто пишет алерт, в зависимости от уровня доверия к детектору.

## 1. Резюме
Легковесная альтернатива EDR/HIDS, написанная как реакция на реальный взлом одного сервера владельца. В README прямо сказано: "Not an antivirus, not an EDR... narrow, auditable safety net". Кодовая база небольшая (~1500 строк bash в `lib/`, `cerberus.sh`, `master.sh`, `ir/`), без внешних рантайм-зависимостей — чистый POSIX/bash + стандартные утилиты (`ps`, `ss`/`netstat`, `iptables`, `md5sum`). Есть только один видимый коммит в клоне ("docs: refresh README"), но CHANGELOG описывает полноценный "v2.0 — full rewrite", то есть история разработки реальна, просто не полностью видна в неглубоком клоне.

## 2. Архитектура
Однопроцессный демон под systemd (`Type=simple`, `Restart=always`), цикл раз в `SENSOR_INTERVAL` секунд: `lib/detect.sh` (детекторы) → `lib/respond.sh` (тиры HARD/SOFT: kill/quarantine/iptables либо только алерт) → `lib/forensics.sh` (сбор улик всегда) → `state/events.jsonl` + `notify()` (log/telegram/webhook/email). `lib/baseline.sh` хранит снэпшот точек персистентности (crontab, cron.d, systemd unit-файлы, authorized_keys, ld.so.preload) и детектит дифф. Сигнатуры (хэши, C2 IP/порты, пути дроппера, паттерны майнеров) вынесены в `etc/signatures/*.txt` — редактируются на лету, без рестарта. Отдельно есть `ir/` — ручные инструменты для реагирования на инцидент (quick_response.sh, emergency_remediation.sh, honeypot.sh, Docker containment), не запускаются демоном автоматически. Архитектура простая, для своего масштаба чистая и явно спроектированная людьми, которые уже обожглись (см. п.4).

## 3. Стадия готовности
Работающий MVP уровня "internal tool", не продукт. Установлен и предположительно эксплуатируется на одном хосте владельца (`WorkingDirectory=/root/projects/eyes_cerberus` захардкожен в systemd-юните). Нет CI/CD, нет автотестов (только ручная "Verifying a change" секция в README с bash-командами для смоук-теста), нет пакетного менеджера/релизов, нет multi-host поддержки "из коробки" — сигнатуры и baseline привязаны к одному серверу. Документация (README, KNOWN_THREATS, CHANGELOG, SECURITY) необычно подробная для однопользовательского инструмента — похоже на подготовку к возможному открытию репозитория/публикации, а не к продажам.

## 4. Технический долг
- Работает только на одном хосте, конфигурация (`etc/cerberus.env`, `WorkingDirectory` в systemd-юните) жёстко привязана к пути `/root/projects/eyes_cerberus` — разворачивание на втором сервере потребует ручной правки.
- Нет автоматических тестов — только ручной чек-лист в README; регрессии (как v1, который тихо не работал неделями из-за `Type=oneshot`+`nohup` и `set -euo pipefail`, убивавшего детекторы на первом пустом `grep`) обнаруживаются постфактум.
- `ir/honeypot.sh` явно помечен "EDUCATIONAL/RESEARCH PURPOSES ONLY" с комментарием про "potentially mislead attackers" — код контр-атаки/обмана присутствует в репозитории, хотя и не включён в автоматический цикл (см. п.11).
- SECURITY.md — шаблонный, с незаполненным `[YOUR_EMAIL_HERE]` вместо реального контакта.
- TODO/FIXME-меток в коде не найдено — скорее означает, что мелкий долг не документируется явно, а не что его нет.

## 5. Зависимости и риски
Внешних зависимостей практически нет (bash + coreutils + `iptables`/`ss`/`ps`), что снижает supply-chain риск почти до нуля — сильная сторона. Обратная сторона: демон требует root (kill произвольных PID, чтение `/proc/<pid>/{exe,environ}`, управление iptables) — любая ошибка в детекторе или конфиге напрямую бьёт по продакшену. README сам документирует прецедент: v1 убивал `unattended-upgrade`, `fwupd`, `pg_dump` из-за грубой CPU-эвристики. Уведомления через Telegram/webhook/email хранят токены в `etc/cerberus.env` (git-ignored — это правильно сделано).

## 6. Блокеры
Продуктовых или монетизационных блокеров нет, потому что монетизация не планировалась изначально (см. п.7). Технических блокеров для дальнейшего использования владельцем — нет, инструмент рабочий. Единственный практический блокер для превращения в продукт — полное отсутствие multi-tenant/multi-host архитектуры и тестового покрытия.

## 7. Принцип монетизации
Монетизация не заложена и не просматривается в коде/README (оценка). Это defensive security tool для собственной инфраструктуры автора, написанный после реального инцидента, а не SaaS/продукт. Гипотетический путь монетизации — open-core модель (бесплатный bash-агент + платная центральная панель агрегации событий с нескольких хостов), но текущая кодовая база к этому не готова.

## 8. Целевая аудитория и рынок
Как есть — аудитория из одного пользователя (сам владелец, для своего сервера). Как потенциальный продукт — соло-разработчики и малый бизнес с 1–10 VPS, которым не по карману/не нужен Wazuh/CrowdSec/коммерческий EDR, но нужна хоть какая-то базовая защита от типовых Linux-дропперов и крипто-майнеров (оценка).

## 9. Конкуренты и уникальное преимущество
Конкуренты — Wazuh, OSSEC, CrowdSec, Falco, fail2ban, коммерческие EDR (SentinelOne, CrowdStrike) — все на порядок функциональнее и с центральным управлением. Уникальное УТП Eyes Cerberus — не функциональность, а простота: единственный bash-файл-демон без агентов, без сервера управления, без внешних runtime-зависимостей, с сигнатурами конкретно под пережитый инцидент. Как нишевый инструмент для тех, кто хочет "видеть, что происходит" без развёртывания тяжёлого SIEM/EDR-стека — жизнеспособен, но рынок узкий и конкуренция с бесплатными зрелыми альтернативами (CrowdSec) сильная (оценка).

## 10. Затраты до монетизации (кроме разработки)
Как есть (личный инструмент) — затраты минимальны: только время автора. Как гипотетический продукт — потребовались бы: инфраструктура для central dashboard/агрегации, покрытие тестами и поддержка нескольких дистрибутивов Linux, юридическая проработка функций активного противодействия (honeypot/обман), полноценная документация по установке под разные окружения (оценка).

## 11. Регуляторные / юридические риски
Несмотря на название ("eyes", "cerberus"), это НЕ инструмент слежки за людьми — это host-based intrusion detection для собственного сервера, направленный на процессы/сетевые соединения, а не на пользователей. Прямых рисков приватности/персональных данных не выявлено. Однако есть два реальных юридических риска:
1. `ir/honeypot.sh` содержит код для создания приманок и "potentially mislead attackers" (введение атакующего в заблуждение) — в некоторых юрисдикциях активное противодействие/"hack-back" может квалифицироваться как неправомерный доступ к чужой системе или создавать встречную ответственность, если атакующий использует скомпрометированный third-party хост. Сам файл содержит явный disclaimer "Consult legal counsel before deploying counter-measures" — авторы это осознают.
2. Автоматический kill процессов и блокировка IP на уровне iptables при ложном срабатывании может нарушить работу стороннего ПО/сервисов на сервере (уже происходило в v1) — это operational/contractual риск, а не regulatory, но стоит держать в уме при коммерциализации (SLA с клиентами).
В остальном — стандартный disclaimer об отсутствии гарантий присутствует (LICENSE MIT, явный disclaimer в README).

## 12. Time-to-revenue
Неприменимо в текущем виде — проект не монетизируется и, судя по всему, не предназначен для этого (оценка). Если бы велась работа над продуктовой версией (managed dashboard), реалистичный time-to-revenue — 3–6 месяцев на MVP панели + пилотных клиентов, но это не то, чем сейчас является репозиторий (оценка).

## 13. Вердикт
**Hold.** Как личный defensive-инструмент — рабочий, аккуратно спроектированный после реального инцидента, годный к дальнейшей эксплуатации на своём сервере. Как бизнес-актив — не готов и не спроектирован для монетизации; чтобы стать продуктом, потребуется отдельная инвестиция в multi-host архитектуру, тесты и юридическую проработку функций активного противодействия.

## 14. Следующий шаг
Заполнить `[YOUR_EMAIL_HERE]` в SECURITY.md реальным контактом и решить: либо оставить проект как есть — приватный/личный инструмент безопасности (в этом случае — просто продолжать эксплуатацию), либо, если есть намерение опубликовать/монетизировать, начать с добавления автотестов (`bats`/shell-тесты для `lib/detect.sh`) и явного юридического решения по судьбе `ir/honeypot.sh` (убрать функции обмана атакующего или чётко ограничить область применения).
